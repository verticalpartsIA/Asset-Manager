Revisão da camada Supabase — Asset Manager

Schema auditado: asset_manager · Projeto Core vpsistema (ubdkoqxfwcraftesgmbw) · PostgreSQL 17
Data: 2026-08-10 10:29 (BRT) Tipo: Auditoria read-only (nenhuma alteração aplicada) Escopo: objetos do schema asset_manager + queries do cliente (public/vp-integration.js)

Sumário executivo

O schema asset_manager está bem isolado e seguro na fundação: RLS habilitada em 100% das tabelas, FKs com ON DELETE coerentes, check constraints nos enums, índices de FK abrangentes e zero achados no advisor de segurança do Supabase. O public do Core (44 tabelas de outros apps) permanece intacto.

Os pontos de atenção concentram-se em duas frentes: (1) a política de RLS é permissiva demais — hoje qualquer colaborador autenticado tem CRUD total (inclusive DELETE) sobre todos os dados; e (2) a ponte de persistência em JSONB (app_state), adotada como estágio híbrido, traz risco de perda de dados em concorrência e amplificação de escrita, além de divergência do espelho tipado assets. Nenhum desses é bloqueante para o uso inicial, mas devem ser endereçados antes da adoção ampla.

Detalhamento

F1AltaRLS permissiva demais — qualquer autenticado tem CRUD/DELETE total

As 21 tabelas têm exatamente uma policy idêntica: am_authenticated_all — FOR ALL TO authenticated USING (true) WITH CHECK (true).

tablename        | cmd | roles           | qual | with_check
assets           | ALL | {authenticated} | true | true
allocations      | ALL | {authenticated} | true | true
tickets          | ALL | {authenticated} | true | true   (… idêntico nas 21)
Objeto
Todas as tabelas de asset_manager (policy am_authenticated_all)
Evidência
pg_policies — using=true, with_check=true, cmd=ALL
Impacto
Qualquer colaborador autenticado (inclusive papel user) pode ler, editar e apagar todos os ativos, alocações, chamados, histórico e logs — chamando a API/PostgREST diretamente. O modelo de papéis (admin/técnico/user) existe só no JavaScript do cliente, que não é fronteira de segurança.
Risco
Exposição/adulteração/exclusão de dados internos por qualquer usuário logado. Alto para um sistema de patrimônio.
Esforço
Médio
Correção
Policies por papel e por comando: SELECT liberado a authenticated; INSERT/UPDATE/DELETE restritos a admin/técnico. Recomendado usar uma função STABLE security definer com search_path fixo que consulte public.profiles.level do auth.uid() (ex.: am_is_staff()), evitando reavaliação cara por linha (envolver em (select …)).
Migração
Sim (novas policies; substitui a permissiva).
F2Média-AltaConcorrência do JSONB — perda de atualização (lost update)
Objeto
asset_manager.app_state + VP.save() em vp-integration.js
Evidência
Cada coleção é uma linha (collection PK) contendo o array inteiro; cada saveData faz upsert do array completo (last-write-wins).
Impacto
Dois usuários (ou duas abas) editando itens diferentes da mesma coleção: o último a salvar sobrescreve as mudanças do outro, sem aviso. Não há validação/constraint por registro dentro do JSONB.
Risco
Perda silenciosa de dados em uso multiusuário — cenário esperado num sistema de TI compartilhado.
Esforço
Médio-Alto
Correção
Promover as entidades centrais para tabelas tipadas com escrita por registro (já planejado para employees/allocations/tickets). Interino: guarda otimista por updated_at (rejeitar upsert se a versão mudou) ou gravação item-a-item.
Migração
Sim (promoção relacional).
F3MédiaEspelho tipado com drift + tabelas tipadas ociosas
Objeto
asset_manager.assets (espelho) e employees/allocations/tickets/… (tipadas, ainda vazias)
Evidência
VP.save popula app_state + espelho de assets (best-effort, não-fatal). DELETE no app não propaga ao espelho; demais tabelas tipadas não são escritas.
Impacto
Consultas/relatórios (Painel Executivo/SQL) sobre asset_manager.assets podem divergir do estado real: itens apagados no app permanecem no espelho; uma falha de espelho passa silenciosa. Relatórios por employees/allocations/tickets ainda não existem por coluna.
Risco
Relatórios/decisões sobre dados inconsistentes.
Esforço
Médio
Correção
Concluir a promoção relacional e propagar DELETE; enquanto isso, documentar que app_state é a fonte de verdade e o espelho é derivado (e reconciliar periodicamente).
Migração
Parcial (código + possível reconciliação de dados).
F4MédiaAmplificação de escrita — reescreve a coleção inteira a cada save
Objeto
VP.save / app_state (e espelho de assets)
Evidência
Salvar 1 ativo reescreve todo o array de assets (JSONB) e faz upsert do array inteiro no espelho — custo O(n) por gravação.
Impacto
Custo de escrita e tamanho de payload crescem com o volume; aumenta a janela de conflito de F2.
Risco
Degradação conforme a base cresce (centenas → milhares de itens).
Esforço
Médio-Alto (mesma correção de F2)
Correção
Escrita por registro em tabelas tipadas; abandonar o rewrite de array por coleção nas entidades quentes.
Migração
Sim.

Pontos fortes (o que já está correto)

  • Isolamento Schema dedicado asset_manager — zero poluição no public do Core (44 tabelas de outros apps intactas).
  • RLS Habilitada em 21/21 tabelas; anon sem grant (bloqueado) — acesso só a authenticated/service_role.
  • Advisor 0 achados de segurança atribuídos ao asset_manager (os lints do projeto são de outros schemas).
  • Integridade FKs com ON DELETE coerentes (CASCADE em filhos; SET NULL nas referências a public.profiles) e reuso da identidade central (nunca duplicou profiles).
  • Constraints CHECK nos enums: assets.status, tickets.priority/status, stock_items.category, checklists.semester, checklist_signatures.role_context.
  • Índices Cobertura ampla de FKs e colunas de filtro; PK em todas as tabelas.
  • Função set_updated_at() com security invoker + search_path = '' — evita o lint function_search_path_mutable.

Plano recomendado (ordem sugerida)

  1. F1 — RLS por papel (segurança primeiro): separar leitura × escrita e restringir escrita a admin/técnico via profiles.level.
  2. F2 + F4 + F3 — Promoção relacional de employees, allocations, tickets (escrita por registro; encerra lost-update, amplificação e drift).
  3. F5 — Versionar migrations no repo (baixo esforço, alto ganho de reprodutibilidade/auditoria).
  4. F7 / F8 — índice em app_state.updated_by e popular assets.type_id (rápidos).
  5. F6 / F9 / F10 — reavaliar após tráfego real (paginação, índice redundante, ANALYZE).

Observação: este relatório é apenas diagnóstico. Nenhuma policy, objeto ou dado foi alterado. As correções acima exigem migrations/ajustes de código a serem aprovados e aplicados em etapa separada.
