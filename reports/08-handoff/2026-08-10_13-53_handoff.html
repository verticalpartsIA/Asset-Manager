3. Arquitetura relevante

  • Frontend: index.html (god-file, script inline) + vp-integration.js (camada de SSO + persistência Supabase). O app usa getData/saveData (localStorage) sincronamente; saveData é envelopado para write-through ao Supabase.
  • Persistência híbrida: assets/employees/allocations → tabelas tipadas (fonte de verdade, gravação por registro: diff → upsert só do que mudou + delete só do que saiu; objeto original em details, leitura lossless). Demais coleções → asset_manager.app_state (JSONB) com merge por registro (evita lost-update).
  • SSO token-only: lê ?sso_token= do card, valida, pega o perfil em public.profiles, deriva o papel de profiles.level. Sem refresh → a sessão cai em F5/expiração (~1h) e o app volta a gravar só no localStorage. Mitigado por um indicador de sincronização.
  • RLS por papel: leitura para qualquer authenticated; escrita só staff (Administrador), via asset_manager.is_staff(). app_state mantém insert/update abertos; delete só staff.
  • Deploy: GitHub Actions → Hostinger estático (SCP de public/*), gera version.json e faz cache-bust do JS por commit (?v=<sha>).

6. Decisões técnicas

  • Schema dedicado asset_manager (não poluir o public do Core, que hospeda o portal + 2 apps).
  • Persistência híbrida (tipado nas entidades centrais; JSONB no resto) — escolha do usuário sobre "só JSONB" ou "tudo relacional".
  • SSO token-only (escolha do usuário) em vez de sameproject com refresh (que exigiria deploy da edge function do portal).
  • Deploy estático (a hospedagem é compartilhada, sem Node) — server.js só p/ dev.
  • RLS: staff = Administrador (níveis reais: Administrador/Lider/Colaborador; só Admin escreve tipado, o que bate com a UI).

9. Bugs / problemas conhecidos

  • Token-only: após F5/expiração (~1h) a sessão Supabase cai e o app grava só no localStorage. Mitigado (indicador de sync avisa e pede reentrar pelo card), não eliminado.
  • Deploy transitório: às vezes falha por i/o timeout de SSH do Hostinger (fail2ban). Solução: re-disparar o workflow (gh workflow run).
  • Ativos não têm DELETE real (só "Descartar" = status). A propagação de DELETE para assets é salvaguarda dormente (correto por design).

10. Riscos conhecidos
